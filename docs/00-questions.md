## A. Назначение и границы

1. **[Б] Что такое «инвентарь» (inventory)?** В CLI `--source/-s <inventory-name>` и `--alias <alias for inventory>`,
   но сущности в реестре названы `cluster`. Это одно и то же или отдельная сущность
   «инвентарь = набор кластеров + учётки + правила обнаружения»?
   _Дефолт: inventory = алиас кластера; отдельной сущности нет._
2. **[Б] Направление репликации**: один source → один destination (как в `add replication -s -d`) или
   нужны many-to-many, цепочки (a→b→c), fan-out и «зеркало» (a→b и a→c)?
   _Дефолт: только source→destination, одна пара на запись, но несколько реплик на пару разрешены._
3. **[Б] Что именно реплицируется по умолчанию?** Только данные (bucket+objects), или также
   настройки бакета (versioning, tags, policy, lifecycle, encryption, CORS, ACL бакета),
   и метаданные объектов (Content-Type, tags, user metadata, storage class, ACL объекта)?
   _Дефолт: реплицируем настройки бакета и метаданные; ACL — только если разрешено access-политикой._
4. **[В] Удаления**: удалённые в источнике объекты/бакеты удаляются на цели (tombstone), или цель только
   накапливает? Есть ли режим «soft delete» с окном?
   _Дефолт: удаления не реплицируются, но фиксируются в stat как `deleted_skipped`._
5. **[В] Версионирование на цели**: переносится ли versioning бакета и версии объектов, или только latest?
   _Дефолт: versioning источника переносится; версии объектов — только latest, если не указано иное._
6. **[М] Однонаправленность данных**: агент только тянет из источника (pull) или ещё и пушит (push)?
   _Дефолт: pull (агент читает источник и пишет цель)._
7. **[М] Нужен ли режим «миграция» (initial full sync) отдельной сущностью от репликации (delta)?
   _Дефолт: нет; первая же репликация делает full, дальше только дельта._

## B. Сборка и зависимости

8. **[Б] Сборка**: CMake, каталог/структура, имя таргета `s3mm`, C++17 или C++20?
   _Дефолт: CMake + C++20, один бинарь `s3mm` (CLI + демон), `src/`, `include/`, `tests/`, `third_party/`._
9. **[Б] S3-клиент**: использовать AWS SDK for C++ (`aws-sdk-cpp`) с SigV4, или писать свой
   HTTP/S3 клиент (libcurl + свой SigV4/OpenSSL, чтобы не тянуть тяжёлую зависимость)?
   Учесть: offline-окружение, лицензии, время сборки.
   _Дефолт: свой клиент на libcurl + OpenSSL, без внешних SDK (кроме libcurl/OpenSSL/SQLite)._
10. **[Б] Хранилище состояния/конфига**: SQLite (встроенный, файл), Postgres, etcd, только JSON-файлы?
    От этого зависит дельта, блокировки, история, `stat`.
    _Дефолт: SQLite (WAL) + версионированная схема; конфиг-артефакты хранятся в ней же._
11. **[В] Зависимости**: доступен ли `apt`/vcpkg/conan в среде сборки? Есть ли уже готовый контейнер?
    Нужны ли fmt/spdlog/json/nlohmann?
    _Дефолт: минимум зависимостей — libcurl, OpenSSL, SQLite3; свой JSON-парсер и логгер._
12. **[М] Тесты**: фреймворк (Catch2 / GoogleTest / doctest), нужен ли мок-S3 (moto/minio в docker)
    или достаточно in-memory фейкового S3-сервера в тестах?
    _Дефолт: собственный минимальный fake-S3 (httptest-сервер на libcurl-сервере) + простой assert-фреймворк без внешних зависимостей._

## C. Кластеры и реестр учётных данных

13. **[Б] Формат адреса**: один endpoint или список (для HA/failover)? Path-style или virtual-hosted?
    Нужны ли TLS, кастомный CA, `--insecure`, HTTP (明文) для тестов?
    _Дефолт: список endpoint-ов с round-robin, path-style, TLS опционален, `--insecure` для самоподписных._
14. **[Б] Типы кластеров**: какие S3-реализации поддерживаем (AWS S3, MinIO, Ceph RGW, VK/Sber/Yandex Cloud, Proxmox)?
    Нужна ли feature-detection (наличие ACL, bucket policy, versioning, multipart, тейминга)?
    _Дефолт: общий подмножество S3 API + feature-detection по capability, спец-адаптеры для MinIO/ Ceph не делаю._
15. **[Б] Учётные данные**: состав записи — `access key`, `secret key`, `session token`, `region`, `endpoint path`,
    роль/ARN, дата истечения, описание? Как хранить секрет (шифрование at-rest, master-key откуда)?
    _Дефолт: access/secret/optional session token/region; секрет шифруется AES-256-GCM ключом из `S3MM_MASTER_KEY` или keyring-файла с 0600._
16. **[Б] Что значит `--zone/-z` в `add credentials`?** Физическая зона/дата-центр, логическая группа для
    маршрутизации реплик, или тег? Влияет ли на выбор источника при нескольких кластерах?
    _Дефолт: свободный тег «зона» для группировки и фильтрации; на маршрутизацию не влияет._
17. **[Б] Одна и та же учётка в нескольких кластерах**: `add credentials --cluster -c <c> -n <acc>` — имя `acc`
    уникально глобально или уникально в пределах кластера? Нужна ли глобальная «identity», чтобы
    access-политика могла匹配 одну и ту же учётку на разных кластерах (ключ для ACL — access key id?)
    _Дефолт: имя уникально в пределах кластера; глобальный ключ политики — access key id (AKID)._
18. **[В] Проверка учёток**: валидировать при добавлении (пробный ListBuckets)? Хранить результат/health?
    Автоматическая ротация секретов?
    _Дефолт: опциональный флаг `--check`, без автоматической ротации._
19. **[Б] Кто читает список учёток/ACL на источнике?** Чтобы реплицировать «учётки», агент должен иметь
    админский доступ (admin API конкретной реализации: MinIO `mc admin`, Ceph RadosGW, AWS IAM).
    Чистым S3-ключом список IAM-пользователей не получить.
    _Дефолт: два режима источника — `s3` (только бакеты/объекты/ACL бакета через S3 API) и
    `admin` (через адаптер реализации, по умолчанию MinIO; для AWS — IAM GetUser/GetAccountSummary)._
20. **[Б] Ключевой блокер — мутация учёток**: «для одного access-key менять secret-key на реплицируемом
    кластере» технически означает **импорт** учётки на целевой кластер. Значит ли требование, что агент
    умеет создавать/менять пользователей на целевом кластере через admin API? Или достаточно
    *описать* трансформацию (policy) и применить, когда целевой кластер это поддерживает,
    а иначе — `warning`?
    _Дефолт: да, нужен слой admin-адаптеров; при отсутствии поддержки — действие `warning` и запись в корзину._

## D. Access (ACL) политики

21. **[Б] Модель ACL**: какие сущности и права? Ниже предложена: subject=`access key id` (или `user`),
    resource=`bucket` (или `bucket/object`), permissions=`READ|WRITE|FULL_CONTROL|ADMIN`.
    Нужны ли group-based гранты (MinIO groups)?
    _Дефолт: subject = access key id, resource = bucket/prefix/object ARN-lite, permissions = перечисленные 4 + `NONE` для deny._
22. **[Б] Синтаксис правил**: использовать DSL в духе firewall (как в примере из ТЗ) или JSON/YAML?
    Нужен ли полный парсер выражений (`AND/OR/NOT`, `=`, `>=`, `IN`) или хватит `key op value`?
    Пример из ТЗ: `object source cluster=... size>=50G action log message='...' level=... drop`
    — заметьте, тут `action log ... drop` (два действия). Подтверждаем, что действий может быть несколько?
    _Дефолт: свой компактный DSL с `AND/OR/NOT`, сравнениями `= != < <= > >= ~` (числа с суффиксами K/M/G/T),
    списком через запятую, и списком действий `action a, b, c`; выражения в одинарных кавычках._
23. **[В] Порядок правил и дефолт**: правила по одной категории упорядочены по приоритету (`order`/`priority`)?
    Что делает неотрендеренный объект/бакет — дефолт из `s3mm policy` (`drop-all`?) или «наследовать/агент-only»?
    _Дефолт: `order` (по умолчанию порядок добавления), первое совпавшее правило выигрывает; глобальный дефолт
    настраивается через `s3mm policy` и по умолчанию `accept` для bucket/object и `accept` для access
    (не `drop-all`) — см. вопрос 26._
24. **[В] Трансформации access**: кроме смены secret и сужения списка бакетов, поддерживаем ли
    `add/remove permission`, `map cluster A->B`, `rename access key`, `mask/rotate secret`,
    `limit prefix`? Нужны ли функции (вычисляемый secret от пароля)?
    _Дефолт: `secret=` (с фиксированным значением или шаблоном), `buckets=` (полный набор, сужение),
    `add-permission=`/`remove-permission=`, `deny-buckets=`, `prefix=`. Без функций и без переименования AKID._
25. **[В] Конфликты**: две политики описывают одну учётку. Merge, приоритет, или ошибка?
    _Дефолт: приоритет по `order`, глубокое слияние на уровне permission-per-bucket._
26. **[Б] `s3mm policy` — точная семантика.** Из ТЗ: «набор действий по умолчанию», есть встроленный артефакт
    `drop-all`. Значит, сущность `policy` — это глобальный набор *действий по умолчанию* для каждой категории
    (access/bucket/object) и для каждого *результата* (denied/success/warning), плюс маршрут по умолчанию?
    Или `policy` — это *набор правил* (набор политик), применяемых ко всем кластерам?
    Или и то и другое: `policy` = профиль/бандл правил + дефолтные действия?
    И как он выбирается: `--policy <name>` при `add replication`, или всегда глобальный?
    Нужны ли несколько именованных policy-бандлов (например, `prod`, `dev`)?
    _Дефолт: `policy` — именованный **бандл правил** (списки acl/bucket/object-правил), выбирается флагом
    `--policy/-p` при `add replication`; внутри бандла есть `default-action` для каждой категории и
    `default-route` для denied/success/warning; встроенный бандл `drop-all` = deny-всё, доступен и создаётся
    автоматически, редактируется через `s3mm policy`/`edit rule`; дефолтный бандл `default` — accept с агентскими правами._

## E. Bucket политики

27. **[Б] Поля проверки бакета**: подтверждаем минимум — `owner`, `type (private/public)`, `name`.
    Что ещё: tags, versioning, encryption, region/location, creation-date, object-count, size,
    bucket-policy (JSON), default ACL, `last-modified`?
    _Дефолт: owner, name, type, tags, versioning, encryption, location, created/last-modified, object-count, total-size, bucket-policy-hash._
28. **[Б] Что именно bucket-политика решает?** Только «создавать ли задачу репликации бакета» (ТЗ 3.5),
    или также «какие настройки бакета переносить» и «создавать ли бакет на цели сразу или лениво»?
    _Дефолт: решает факт создания задачи; дополнительно поле `propagate=[settings]` задаёт перенос настроек бакета._
29. **[В] Несовпадение ни с одним правилом**: пропускаем бакет молча, `warning`, или `denied`?
    _Дефолт: срабатывает `default-action` категории bucket (по умолчанию `accept`)._
30. **[В] Уже существующий на цели бакет**: пропустить/переиспользовать/пересоздать? Нужно ли сравнивать
    настройки и обновлять их (это тоже дельта)?
    _Дефолт: переиспользовать; настройки обновляются, если изменились (дельта по хэшу настроек)._

## F. Object политики

31. **[Б] Доступные атрибуты объекта**: подтверждаем `name` (полное и relative), `extension`,
    `content-type`, «фактический формат» (по magic-байтам), `size`, `chunk count` (число multipart-частей),
    плюс `etag`, `last-modified`, `storage-class`, `checksum`, `tags`, `acl`, `encrypted`,
    `key-count` (число ключей шифрования SSE-KMS). Что ещё нужно?
    _Дефолт: весь список выше._
32. **[Б] Как определять «фактический формат»**: нужно ли качать начало объекта (range GET) для magic-бит
    для каждого объекта? Это убийственно для больших данных. Варианты: (a) только заголовок+расширение,
    (b) Range GET первых 8KB один раз и кэш в состоянии, (c) только если в правиле есть `format=`.
    _Дефолт: (c) — magic-читым лениво, только когда в правилах категории object встречается `format=`/`mime=`,
    с кэшем в состоянии по etag+size; иначе `format` = content-type без скачивания._
33. **[Б] Где применяются объектные политики**: ко всем объектам при *сканировании* (по метаданным из
    ListObjects/HeadObject) — верно? Тогда отфильтрованные объекты не скачиваются вовсе (важно для скорости).
    Или есть правила, требующие тела (например, DLP по содержимому)?
    _Дефолт: только по метаданным; правил по содержимому нет; тело читается только для объектов,
    прошедших фильтр._
34. **[Б] Словарь действий**: `accept`, `drop`, `log`, `quarantine`/`caratine` (упомянута кастомная),
    `replicate`, `defer/retry`, `tag`? Действие может быть кастомным (пользовательское имя)?
    Своё кастомное действие без привязки к реальному обработчику — что оно делает (noop+лог)?
    _Дефолт: accept, drop, log, quarantine, defer, и произвольные имена через custom-handler (по умолчанию log+noop)._
35. **[В] Куда попадает объект по результату**: одна корзина на действие или на исход действия+код?
    Что в `warning` — таймаут, ошибка чтения, отсутствие admin-доступа, превышение лимитов, ошибка записи?
    _Дефолт: корзина = исход действия; в warning попадают soft-ошибки (429/5xx/таймауты/лимиты), в denied —
    решения политик (drop/filter), в success — успешно доставленные._

## G. Планировщик, дельта, батчинг

36. **[Б] «Все политики — отдельные потоки»**: реально OS-пул на каждое правило (масштабируется лично)?
    Или «отдельный поток» = отдельная очередь/воркер-группа (логическая изоляция)?
    Сколько правил ожидается (10 / 1000)?
    _Дефолт: логическая изоляция — пул воркеров + отдельная очередь на правило, без создания OS-треда на каждое правило._
37. **[Б] Детект дельты (3.6)**: источник истины — (a) ListObjects + сравнение (etag,size,last-modified)
    с состоянием, (b) S3 Inventory/bucket notifications, (c) Versioning + delete-markers,
    (d) CloudTrail/IAM-аудит? Нужна ли поддержка нескольких методов?
    Что делать при отсутствии versioning и массовых изменениях (миллионы объектов)?
    _Дефолт: метод (a) как базовый + (b) если у источника включён Inventory (опционально);
    List — с пагинацией и rate-limit; состояние в SQLite._
38. **[Б] Повторная репликация при изменении политики**: если правило изменилось и объект теперь должен
    реплицироваться, но сам объект не менялся — копировать? И наоборот: объект изменился, но новое
    правило его `drop` — не копировать?
    _Дефолт: копировать (политика — часть входных данных дельты: при изменении policy-хэша
    помечаем соответствующие объекты/бакеты как «требуют переоценки»); drop — всегда выигрывает._
39. **[Б] Пороги отправки (3.8)**: `replication queue --size/-s` — это «сколько байт накопить», а
    `replication period --time/-t` — «как долго ждать»; срабатывает **любое** из двух. Верно?
    Что важнее по умолчанию (size-first, time-first)? Есть ли минимальный размер партии
    (не отправлять 1 объект каждые 5 секунд)?
    Область действия порога: на реплику / на связку / на бакет?
    _Дефолт: OR-триггер; размер важнее (проверяем размер первым); `min-size` по умолчанию 1 MiB;
    пороги на каждую реплику._
40. **[Б] Персистентность очереди**: очереди/корзины/задачи переживают рестарт? Что происходит при
    падении во время отгрузки — докачиваем с места обрыва (part-level resume) или перекачиваем заново?
    _Дефолт: да, всё в SQLite; возобновление по multipart-upload + чекпоинту по объекту._
41. **[В] Ограничения**: нужен ли rate-limit запросов к источнике/цели, bandwidth cap, максимум параллельных
    задач на кластер, минимальный размер part, таймауты и ретраи (экспоненциальные, с jitter)?
    _Дефолт: все настраиваемые в `s3mm` config: 4 параллельных transfer-а на кластер,
    part-size 16 MiB (для multipart), retry 5 с backoff+jitter, rate-limit опционален._

## H. Задачи, корзины, маршрутизация

42. **[Б] Границы «общего ящика» (3.9)**: одна задача = (реплика × скан-цикл), или (реплика × бакет)?
    Корзины (`denied|success|warning`) — глобальные на реплику или на каждую задачу? Видны ли они через
    `s3mm replication list` все сразу или с фильтром по задаче/кластеру?
    _Дефолт: задача = (реплика × бакет × цикл сканирования); корзины персистентны и накапливают записи,
    `list` показывает накопленное с фильтрами._
43. **[Б] Типы целей репликации**: кроме `null` (drop) — какие? Локальный каталог, S3-путь на
    «карантинном» кластере, HTTP/webhook, syslog, запись только в БД? Синтаксис?
    _Дефолт: `null`, `file:/path[/template]`, `s3://cluster/bucket/prefix`, `http(s)://…` (webhook), `db` (внутр. таблица);
    шаблоны пути с плейсхолдерами `{task}`, `{bucket}`, `{key}`, `{action}`, `{ts}`, `{reason}`._
44. **[Б] `replication --replica -r route <bucket> --cluster -c <name>`**: это разовое действие
    «перенаправить накопленное из корзины X в кластер C», или изменение маршрута-по-умолчанию
    для этой корзины (на будущее)? Или и то и другое (`--once` флаг)?
    Что делать с уже отгруженным в `null` (drop) — необратимо, верно?
    _Дефолт: по умолчанию изменение маршрута для будущих записей + немедленный «слив» накопленного
    в корзине (флажок `--no-flush`); в `null`-корзину слив невозможен — `dropped` безвозвратно (в БД остаётся запись)._
45. **[В] Когда чистится корзина**: после отгрузки записи удаляются? Хранятся ли записи `success` для аудита,
    с TTL? Нужна ли команда `s3mm replication prune/rm`?
    _Дефолт: после успешной отгрузки запись помечается `shipped` и хранится N дней (TTL из конфига, дефолт 7); prune-команда есть._
46. **[М] Нужна ли поддержка «карантинного» действия как первоклассной сущности**, т.е.
    `add replication --quarantine-target ...`, или достаточно route-ов и кастомных действий в правилах?

## I. CLI
